# E3 - Mobile como herramienta de trabajo

Base revisada: v1.14.1 (`4c521f9`, previa al rebrand), config v10 (`CONFIG_VERSION = 10` en `src/shared/types.ts`), `PROTOCOL_VERSION = 1`. El producto ya esta renombrado a SnAgentsOS (E0, v2.0.0). Este epic cubre los pasos M10 a M14 de la sintesis y la pantalla Changes mobile. Los ctl, mensajes WS, rutas HTTP, canales IPC y claves de config de este PRD salen de la seccion "Contratos compartidos" del plan. Si algo de este PRD la contradice, gana esa seccion.

## Objetivo y problema

Hoy el celu sirve para mirar y teclear, pero no para trabajar. Un pane de 120 columnas se ve con letra de 8px y hay que panear de costado: el v1 decidio que el celu nunca cambia el tamano del PTY (`src/mobile/src/lib/fit.ts`). Desde el celu no se le puede mandar una captura al agente, ni leer la conversacion de Claude como un chat, ni retomar una sesion vieja, ni revisar el diff de lo que hizo el agente. Fuera de casa tampoco llegan avisos con el celu bloqueado, salvo por Discord. Este epic convierte al celu en una herramienta para seguir y dirigir agentes desde el sillon o desde la calle. Suma tamano propio para el celu, vista de chat, envio de imagenes, historial, revision de cambios y un modo HTTPS con Web Push.

## Alcance (in) / Fuera de alcance (out)

**In**
- Transversal:
  - Disponibilidad de cada funcion segun campos del contrato (`authOk.httpToken`, `authOk.pushKey`, `RemotePaneStatus.provider`), sin negociacion de features. El bundle mobile lo sirve el mismo desktop y un bundle viejo se detecta con el "Recargar" de M2 (E1).
  - Rate limit por sesion para los mensajes y ctl nuevos.
  - Timeouts en el cliente.
  - Pegado seguro desde el celu (saneado, bracketed paste y troceo) armado en el cliente sobre el `input` existente, sin mensaje nuevo.
  - Cambios aditivos al protocolo, sin subir `PROTOCOL_VERSION`.
- M10, imagen al agente: la imagen se elige con `<input type=file>`, se reduce en el celu y se sube por `POST /api/upload` con `Authorization: Bearer <httpToken>`. El path devuelto se inserta en el composer o en el PTY.
- M11, modo celular: el celu define cols/rows del PTY con el ctl `fitPane`. El desktop retiene su baseline y muestra un banner con Recuperar. Incluye:
  - Reglas de dueno con varios dispositivos y resize del desktop.
  - Mensaje `fitState`.
  - Replay sin basura tras un cambio de ancho (emulador headless de E5).
  - Estado de dueno conservado al remontar.
- M12, vista Chat para Claude (Codex como P2): se arma desde el transcript JSONL con un watcher incremental (`chatSub`/`chatPage`/`chatAppend`). Mientras se ve el chat, el celu se desuscribe del stream de xterm (`unsub`) y vuelve con `sub`.
- M13: historial de sesiones Claude/Codex (`historyReq`/`historyRes`) con busqueda, "Retomar en consola nueva" (`createPane.resume`) e "Ir a la consola".
- M14:
  - Modo HTTPS por Tailscale (`tailscale serve`).
  - Service worker con estrategia network-first.
  - Web Push con VAPID (`authOk.pushKey`, `POST /api/push/subscribe`).
  - `clipboard.readText`, Wake Lock y QR con camara en vivo.
- Changes mobile: estado git y diff paginados (`gitReq`/`gitRes`) con el lector git de E5, mas notas de revision redactadas en el celu y enviadas con el ctl `sendReviewNotes` (formato de E6).

**Out**
- Commit, push o stage desde el celu (sintesis, seccion 4).
- Responder permisos dejando abierto el hook PermissionRequest. Se mantiene el "1"/Esc de M7, en E2.
- Relay cloud y push via APNs/FCM propio. Web Push usa los servicios de push del navegador, sin servidor intermedio.
- Tailscale Funnel: nunca se usa ni se habilita.
- Modo `manualCert` (certificado propio): pasa a la lista "mas adelante".
- Negociacion de features y ajustes de desktop para apagar cada funcion (imagenes, chat, historial, push). Solo existen `settings.remote.phoneFit` y `settings.remote.https`.
- Dictado propio (Web Speech) y STT local. Alcanza con el microfono del teclado dentro del composer.
- Chat e imagenes para panes SSH/WSL (el transcript o el path no son locales), y ACP o sesiones estructuradas.
- Sincronizar las notas de revision entre el celu y el panel del desktop.
- Paginacion del historial, "Ver completo" de la salida de tools y lectura en Chat de una sesion que no esta abierta.
- Panel de historial en el desktop (fuera de E3; `sessions:list` queda listo para que lo use el desktop).
- Subir archivos que no sean imagen (PDF, zip, etc.).
- Retomar con `--fork-session` una sesion que ya esta abierta (ver Riesgos).

## Historias de usuario

- Como usuario quiero sacarle una foto a un bug en otra pantalla y mandarsela a Claude desde el celu, para no tener que pasar por la PC.
- Como usuario quiero que la consola que manejo desde el celu tenga el ancho del telefono, para leer a 13px sin panear.
- Como usuario quiero que la PC me diga claramente que el celu tiene el control y poder recuperarlo con un clic, para no encontrarme una consola angosta sin saber por que.
- Como usuario quiero leer la conversacion de Claude como un chat, con las tools plegadas y los diffs coloreados, para seguir el trabajo sin pelear con una TUI achicada.
- Como usuario quiero escribir un prompt de varias lineas desde el chat y que llegue como un solo mensaje, para no mandar prompts a medias.
- Como usuario quiero buscar una sesion de ayer y retomarla con un tap, para no tener que acordarme de `claude --resume <id>`.
- Como usuario quiero revisar en el celu el diff de lo que hizo el agente y dejarle notas por linea, para corregirlo desde cualquier lado.
- Como usuario quiero una notificacion con el celu bloqueado cuando un agente necesita permiso, para no tener que estar mirando la pantalla.
- Como usuario quiero que la pantalla no se apague mientras miro una consola y poder pegar el portapapeles con un tap, para que el celu se sienta una app y no una pagina.

## Diseno tecnico

### Correcciones a la sintesis y al draft anterior (verificadas contra el codigo)

1. **`maxPayload` de 64KB** (`MAX_PAYLOAD` en `src/main/remote/RemoteServer.ts`) limita solo los frames de celu a desktop y no cambia. Los frames de desktop a celu no tienen tope, pero igual se paginan a 48KB o menos (FR-02): un frame grande demora los `out` del terminal y empuja hacia `BACKPRESSURE_DROP` (512KB) en `SessionManager.ts`.
2. **`fitPane` es un `ctl` (contrato), pero el tamano del PTY lo aplica main** (`PtyManager.resize`). Los `ctl` se reenvian al renderer (`RemoteManager.executeCommand` -> `src/renderer/lib/remoteCommands.ts`). Por eso `RemoteManager.executeCommand` intercepta `fitPane`/`releaseFit` para registrar el dueno en `FitController` antes de reenviarlos al executor, que redimensiona el xterm del desktop y el PTY por la API existente.
3. **El celu hoy no se entera de los resize**: solo el `replay` trae cols/rows. Hacen falta el mensaje `fitState` (FR-12) y un hook `onResize` en `PtySink`.
4. **No subir `PROTOCOL_VERSION`**. `SessionManager.onMessage` responde `err {code:'version'}` antes del handshake (L206), y `client.ts` ignora los `err` (`case 'err': break`). Un celu con un bundle viejo quedaria colgado en "Conectando". Los cambios son aditivos y el celu decide que mostrar con campos del contrato (FR-01).
5. **`client.ts` ignora `err`**: por eso FR-03 no contesta el rate de los mensajes nuevos (descarte mas timeout de FR-04) y los ctl usan el `ctlAck` existente.
6. **`HookServer` descarta `transcript_path`** del payload de Claude. Hay que sumarlo a `HookEvent` (`cwd` y `sessionId` los agrega E4).
7. **`src/main/usage/custom.ts` ignora `CLAUDE_CONFIG_DIR`**, mientras que `HookInstaller.ts` lo respeta. Chat e historial resuelven la raiz con `process.env.CLAUDE_CONFIG_DIR || ~/.claude`.
8. **El QR en vivo ya existe** en `src/mobile/src/components/ScanScreen.tsx`.
9. **El invariante "There are no REST endpoints"** del header de `RemoteServer.ts` se rompe a proposito con `POST /api/upload` y `POST /api/push/subscribe`, compensado con el `httpToken` (32 bytes aleatorios, ligado a la sesion WS autenticada, invalido al cerrar el socket o revocar el device) mas validacion de Host y Origin. Se actualiza el comentario.
10. **Correccion al draft: el replay NO trae el tamano correcto "sin tocar nada"**. `getReplay` devuelve `entry.history.join('')` (`PtyManager.ts`): bytes crudos emitidos con el ancho anterior, con movimientos de cursor absolutos de la TUI. Con M11 el ancho oscila (por ejemplo 120 <-> 50), y repintar esa historia en otro ancho deja basura. Lo resuelve FR-22 con el emulador headless de E5 (v2.2) y un fallback. Afecta tambien a `reattach` del desktop.
11. **Correccion al draft: detectar input del desktop en `PTY_WRITE` da falsos positivos**. El renderer tambien escribe por `broadcastPrompt.ts` (globalPrompt del celu), `usePaneScheduler.ts`, `insertToConsole.ts` y las respuestas automaticas de `term.onData` en `useXterm.ts` (DA/DSR, focus y mouse reports). Se usa el canal `remote:fitRelease`, emitido solo desde `attachCustomKeyEventHandler` (keydown real) y desde el evento paste.
12. **El composer no puede usar `term.paste()` en Chat**. `PasteSheet.tsx` envia con `term.paste(text)`, que solo envuelve en bracketed paste si el xterm **del celu** vio DECSET 2004. En Chat ese xterm no parsea el stream, asi que las lineas saldrian como Enter. Hoy nadie sigue `2004` en main (sin coincidencias en `src`). Por eso el celu arma el bracketed paste en el cliente (FR-05) con el ultimo modo visto, o asumiendolo para Claude/Codex. Las notas de FR-55 se pegan desde el xterm del desktop, que si conoce el modo real.
13. **`resolveLaunch` aplica el Connection Profile del workspace** (`pane.setupId ?? workspace.setupId` en `src/renderer/lib/launch.ts`). Un resume en un workspace con perfil SSH correria en el host remoto. FR-39 fija `setupId: ''`, porque `??` solo cae con valores nullish.
14. **El snapshot remoto no trae cwd ni setupId** (`src/renderer/lib/remoteSnapshot.ts`, `RemotePaneInfo` = id/title/type/color/icon/running). E3 no agrega un campo `local`: el celu no sabe si un pane es remoto (FR-06). Los cwd del historial y del resume los resuelve main desde `ConfigStore` (en `src/main/index.ts` ya se usa `configStore.load()`) y desde el indice de `SessionHistory`.
15. **`registerPtyIpc(ptyManager)` se registra al arrancar la app** (`src/main/index.ts`), mientras que `RemoteManager` solo crea el server cuando esta prendido. El arbitraje del tamano vive en el renderer (`fitStore`, alimentado por el executor); main solo lleva `FitController` para dueno, gracia y restauracion, sin arbitro en `PtyManager` y sin cambiar la forma de `registerPtyIpc`.
16. **`RemoteEndpoint` exige `ip: string`** (`src/shared/ipc-contract.ts`). El endpoint `tailscaleHttps` no tiene IP, asi que `ip` pasa a opcional y se suma `host`.
17. **El draft anterior usaba mensajes propios** (`paste`, `size`, `uploadReq`/`uploadTicket`, `chatState`, `chatReset`, `chatDetail`, `chatPageReq`, `historyList`/`historyPage`, `resume`, `gitStatus`/`gitDiff`, CRUD de notas, `pushSub`/`pushAck`, `presence`) y un campo `features`. Se reemplazan por los del contrato compartido.

## Requisitos no funcionales

- **Rendimiento**
  - Main:
    - Primera pagina del chat en menos de 300ms. Decodificacion de un append en menos de 20ms cada 100 lineas.
    - Un watcher usa menos de 2MB y hay 4 como maximo.
    - Escaneo hacia atras de 8MB como maximo por pagina.
    - `historyRes` de "Este workspace" en menos de 500ms con 300 sesiones.
    - Ninguna operacion de E3 hace I/O sincronico de mas de 64KB en el hilo principal.
  - Celu:
    - Downscale de 12MP en menos de 1.5s en un telefono de gama media.
    - ChatView a 60fps con 500 mensajes (`content-visibility: auto` por fila).
    - Como maximo 1 `fitPane` cada 150ms por pane, y ninguno por abrir o cerrar el teclado.
  - Red: frames nuevos de 48KB o menos. En Chat el stream de xterm queda pausado (`unsub`).
- **Seguridad**
  - Todo mensaje y ctl nuevo pasa por zod y por el filtro post-auth.
  - Rutas HTTP: Bearer `httpToken` por sesion (invalido al cerrar el socket o revocar), Origin, Host, magic bytes, nombres generados por el server, sin GET, y limpieza solo de nombres generados.
  - Transcripts: admision por `realpath` y asignacion unica (sin cruces entre panes). Markdown sin HTML.
  - Resume: id validado contra el indice; cwd y setupId los pone main/renderer; nunca se ejecuta en un host remoto.
  - Pegado desde el celu y notas: sin ESC ni C0/C1.
  - Push: payload sin texto del agente, allow-list de hosts, claves VAPID en `dataDir()/push-keys.json` (fuera de `config.json`), `subject` sin datos personales.
  - HTTPS: Host exacto solo desde loopback, nunca Funnel.
  - Los logs de diagnostico (E2 M9) redactan el `httpToken` y los endpoints de push.
- **Windows**
  - Paths de adjuntos siempre entre comillas dobles.
  - `fs.watch` con poll de respaldo.
  - El portable guarda `attachments/` y `push-keys.json` bajo `dataDir()`, junto al exe.
  - `tailscale.exe` en Program Files.
  - JSON en UTF-8 sin BOM.
  - Comparacion de rutas case-insensitive.
  - Banner y escalado de fuente probados a 125% y 150% de escala.
- **Accesibilidad**
  - Tap targets de 44px como minimo y `aria-label` en los iconos.
  - El chat usa `role="log"` con `aria-live="polite"` solo para el mensaje final del asistente.
  - Se respeta `prefers-reduced-motion`.
  - Diffs con contraste AA y prefijo +/- como texto.
- **i18n**: todas las cadenas nuevas van en `src/mobile/src/lib/i18n.ts` y en el i18n del renderer, en es y en, con el estilo actual (sin tildes en las cadenas). Las fechas relativas usan `Intl.RelativeTimeFormat` con el idioma del snapshot.
- **Compatibilidad**
  - Un bundle viejo en cache sigue funcionando hasta el "Recargar" de M2 (E1): no envia los mensajes nuevos e ignora los S->C que no conoce.
  - Push requiere iOS 16.4+ (PWA instalada) o Android Chrome 110+.
